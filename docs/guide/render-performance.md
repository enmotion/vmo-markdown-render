# Render 性能压测

2026-11-03 在 Apple M2（8 核、24 GiB 内存）、macOS arm64、Chrome 156.0.8078.80 上执行。测试基于 `edaef85` 的组件实现，增加了独立压测工具，没有修改组件行为。普通模式与 Chrome CPU 降速 4 倍各运行一次，均通过内容就绪、组件错误和浏览器异常检查。

## 方法与复现

```bash
# 使用 Playwright 自带的 Chromium；首次使用需安装浏览器
npx playwright install chromium
npm run test:perf

# 较慢 CPU 的敏感性测试
PERF_CPU_RATE=4 npm run test:perf

# macOS 也可以使用本机 Chrome
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' npm run test:perf
```

脚本先检查压测代码类型，再用独立 Vite 配置做生产构建，启动本机 `127.0.0.1:1981` 服务，最后由 Playwright 单 worker 执行。浏览器视口 1440 × 1000，内容区宽 960px，不加载演示应用。压测独立于常规 `test:browser`，避免影响功能回归的耗时。

结果输出到 `test-results/render-performance-1x.json`、`test-results/render-performance-4x.json`，同时作为 Playwright 附件保存。此目录被 Git 忽略；本文记录本轮摘要，重新执行会覆盖对应倍率的 JSON。

- `commitMs`：赋值 props → Vue `nextTick` → 强制布局，包含同步解析、VNode 生成、DOM 更新和当前布局成本。它不是纯解析时间，也不等于实际像素绘制完成时间。
- `frameReadyMs`：在 commit 后再等两个 `requestAnimationFrame`。这个等待本身就会增加帧间隔，不能拿它计算实际 FPS 或掉帧率；JSON 保留该值供观察。
- 普通内容先预热组件；解析每种长度采样 20 次，首次挂载采样 7 次。表中挂载使用 P50，7 个样本不足以可靠描述尾延迟。
- 流式每组 60 次累计内容更新，使用 `streaming=true`，结束后再设为 `false`。每次完成并等待两个 rAF 后才发送下一次，不模拟固定频率网络输入或排队积压。
- 增强内容等待全部目标节点出现、字体就绪及布局完成，再等两个 rAF。冷/热各测一次；冷指该类增强在本页面首次调用，包含本地资源加载，不代表真实互联网冷启动。

## 普通文档首次挂载

文档由标题、中文正文、强调、链接、行内代码、列表、引用和表格重复组成。字符数按 JS 字符串长度计算，不是 UTF-8 字节数。该样本的结构较密集，不能仅凭字符数推断所有文档的耗时。

| 字符数 | DOM 元素数 | 解析 P50 | 挂载及布局 P50 | CPU 降速 4 倍：挂载及布局 P50 |
| --- | ---: | ---: | ---: | ---: |
| 10,000 | 1,371 | 1.1ms | 8.5ms | 31.6ms |
| 50,000 | 6,860 | 4.6ms | 32.9ms | 130.5ms |
| 200,000 | 27,451 | 19.6ms | 122.1ms | 549.9ms |
| 500,000 | 68,630 | 50.4ms | 316.7ms | 1,340.9ms |

解析与挂载是分别采样，不能把两组中位数相减当成精确分阶段剖析。不过，这轮数据表明只测解析器会显著低估大文档的整体成本。

## 流式更新

“尾部追加”先挂载完整基底，之后每次在尾部多追加 7 个字符；“从空增长”分 60 次增长到目标长度。尾部追加测试到第 60 次比基底多 427 个字符。

| 场景 | 更新 P50 | 更新 P95 | 最慢一次 | CPU 降速 4 倍：更新 P95 |
| --- | ---: | ---: | ---: | ---: |
| 50,000 字符基底，尾部追加 | 11.1ms | 11.5ms | 12.6ms | 40.3ms |
| 200,000 字符基底，尾部追加 | 38.9ms | 44.8ms | 134.4ms | 193.5ms |
| 从空增长到 50,000 字符 | 8.0ms | 11.7ms | 22.2ms | 39.4ms |

在普通 CPU 模式下，20 万字符尾部追加的 60 次更新全部超过 16.7ms，其中 3 次超过 50ms。CPU 降速 4 倍时，该场景 60 次全部超过 50ms。这里统计的是 commit 耗时超过参考阈值的次数，没有通过帧轨迹测量实际掉帧。

流式结束时的最终重解析，5 万字符约 9.6ms，20 万字符约 30.5ms；CPU 降速 4 倍时分别约 30.1ms、130.9ms。

## 增强内容与多实例

下表为全部增强内容就绪时间，包含方法中说明的检查与 rAF 等待，单次样本只用来观察数量级。

| 内容 | 首次调用 | 再次调用 | CPU 降速 4 倍：首次 / 再次 |
| --- | ---: | ---: | ---: |
| 100 个 TypeScript 代码块，每块两行 | 66.7ms | 66.6ms | 107.3 / 67.6ms |
| 100 个求和公式 | 99.3ms | 66.6ms | 365.7 / 232.6ms |
| 20 个 Mermaid 图，每图 3 个节点 | 333.3ms | 266.7ms | 1,365.9 / 1,249.6ms |

同时挂载 20 个 Render，每个 1 万字符，总共 27,420 个 DOM 元素，commit 为 125.4ms；CPU 降速 4 倍时为 546.3ms。所有实例与增强内容均成功渲染，没有上报组件错误或浏览器异常。

## 挂载与卸载

先预热同一生命周期，再对 5 万字符文档重复挂载/卸载 20 次，前后通过 Chrome CDP 强制 GC 后取样：

| 指标 | 普通 CPU | CPU 降速 4 倍 |
| --- | ---: | ---: |
| JS 堆保留增量 | 15,628 bytes | 39,600 bytes |
| DOM 节点数，前 → 后 | 118 → 118 | 118 → 118 |
| JS 事件监听器数，前 → 后 | 14 → 14 | 14 → 14 |

这轮普通文档生命周期没有出现明显的节点、监听器累积。20 次循环、JS 堆及 DOM 计数不能证明不存在内存泄漏，也没有覆盖图片预览、媒体播放和增强库的反复交互。

## 当前判断

这组混合文档中，1 万字符的普通挂载成本较低，5 万字符开始出现可见的单次工作量；20 万至 50 万字符的大文档以及大量 Mermaid，需要单独考虑交互响应。CPU 降速 4 倍明显放大这些成本，但这不等同于特定手机实测。

源码中的 `createEngine` 会在每次调用时重新补全（流式模式）、解析并转换整份输入；Render 随文档变化再次递归生成 VNode。结合尾部小量追加仍随基底长度变慢的结果，后续优先评估：

1. 合并过于频繁的流式 props 更新，减少重复解析；基底已经很大时，仅合并更新不能消除每次的全量成本。
2. 缓存已完成块的解析和渲染结果，限制流式重算范围，同时验证表格、列表、脚注与未闭合语法的边界。
3. 对长文和大量历史消息做分段展示或虚拟化，减少同时存在的 DOM 与实例。
4. 对大量图表评估进入可视区域后再增强，保留源码和错误回退体验。

这些是本轮结果和源码支持的优化方向，尚未实施或验证优化收益。压测没有覆盖业务自定义组件、正文替换规则、远程图片解码、音视频下载、真实移动端、其他浏览器或长时间运行；数据也不构成固定性能承诺。脚本校验内容与错误，不把机器相关的毫秒数设为易波动的 CI 硬门槛。
